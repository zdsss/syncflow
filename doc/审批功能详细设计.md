## 前置约定

### 状态编码统一表

| 状态码 | 含义 | 英文标识 | 适用实体 |
|--------|------|---------|---------|
| 1 | 草稿/编辑中 | DRAFT / EDITING | BOM, Task, ModuleSpec, ProcessRoute |
| 2 | 审批中 | PENDING_APPROVAL | 所有通过 wf_business_object 审批的实体 |
| 3 | 已通过/已发布 | APPROVED / PUBLISHED | 所有实体 |
| 4 | 已驳回 | REJECTED | 所有实体 |
| 5 | 已撤回/已取消 | WITHDRAWN / CANCELLED | 所有实体 |

### BPMN Process Key 约定

| Process Key | 当前状态 | 复用范围 |
|-------------|---------|---------|
| BOM_APPROVAL | 已实现 | BOM 首次发布审批 |
| CHANGE_APPROVAL | 已实现 | 通用变更审批（BOM/工艺/规格等变更共用） |
| STAGE_GATE_APPROVAL | 已实现 | 阶段门审批 |
| PROCESS_APPROVAL | 已实现 | 工艺路线首次发布审批 |
| MODULE_SPEC_APPROVAL | 已实现 | 模块规格首次发布审批 |
| FILE_APPROVAL | 已实现 | 文件发布审批 |
| GENERIC_APPROVAL | 已实现 | 通用单节点审批 |

### 审批人解析规则类型

| 规则类型 | 说明 | ApprovalAssigneeResolver 方法 |
|---------|------|------------------------------|
| PROJECT_ROLE | 按项目角色查 prj_project_member | resolveByProjectRole() |
| DEPARTMENT | 按申请人部门或指定部门 | resolveByDepartment() |
| USER | 直接指定用户 ID | resolveByUserIds() |
| DYNAMIC | SpEL 表达式 (TODO) | resolveByExpression() |

### 当前代码中缺失的关键衔接

现有 `WorkflowService.startProcess()` 能启动任意 BPMN 流程，`ApprovalEventListener` 能动态解析审批人，但**各业务模块的 Service 方法尚未调用 `startProcess()`**，除了 `BomServiceImpl.submitForApproval()` 和 `ProcessRouteServiceImpl.submitForApproval()`。以下设计将聚焦于：何时调用、用什么 processKey、传什么参数、审批后回调做什么。

### 场景 1: 里程碑审批

#### 业务规则

当里程碑的所有子任务均已完成，或责任人手动标记里程碑"完成"时，触发审批流程。里程碑审批的目标是确认里程碑的交付物确实满足验收标准。

**触发条件**：`Milestone.assigneeId` 调用完成里程碑操作，且里程碑当前状态为 `2`（in_progress）。

**不触发条件**：里程碑状态为 `1`（not_started）、`3`（completed）、`4`（delayed），或里程碑没有关联的交付物（deliverable 为空时直接通过，不走审批）。

#### 触发点

**服务方法**：`ProjectService`（或新增 `MilestoneService`）中的 `completeMilestone(Long milestoneId)` 方法。

**当前状态**：`Milestone` 实体已有 `flowInstanceId` 和 `taskId` 字段（见 `prj_milestone` 表），但无任何方法调用 `WorkflowService.startProcess()`。

**实现方式**：

```
// MilestoneService.completeMilestone(milestoneId)
1. 校验: milestone.status == 2 (in_progress)
2. 如果 milestone.deliverable 为空 → 直接完成, 不走审批
3. 设置 milestone.status = 2 (PENDING_APPROVAL 的本地标记, 与 workflow status 对齐)
4. 调用 workflowService.startProcess(
       processKey  = "GENERIC_APPROVAL",
       objectId    = milestone.id,
       objectType  = "MILESTONE",
       objectName  = milestone.name,
       projectId   = milestone.projectId,
       applicantId = milestone.assigneeId
   )
5. 将返回的 flowInstanceId 写入 milestone.flowInstanceId
```

#### BPMN 流程

**复用 `GENERIC_APPROVAL`** -- 单节点审批。

```
startEvent → submit(申请人) → pmApproval(项目经理) → endApproved / endRejected
```

理由：里程碑是项目层级的管控点，只需项目经理一人的确认即可，无需多级审批链。若未来需要更复杂的审批，可切换为自定义 BPMN。

#### 审批链

| 顺序 | 节点 ID | 节点名称 | 审批人规则 | ruleType | ruleValue |
|------|---------|---------|-----------|----------|-----------|
| 1 | pmApproval | 项目经理批准 | 项目中的 PM 角色 | PROJECT_ROLE | PM |

#### 审批人解析

节点 `pmApproval` 使用 `PROJECT_ROLE` 类型，`ruleValue = "PM"`。`ApprovalAssigneeResolver.resolveByProjectRole("PM", projectId)` 从 `prj_project_member` 表查询该项目中角色为 PM 的用户。

**wf_approval_config 初始数据**：

```sql
INSERT INTO wf_approval_config (object_type, process_key, node_id, node_name, rule_type, rule_value, priority, enabled)
VALUES ('MILESTONE', 'GENERIC_APPROVAL', 'pmApproval', '项目经理批准', 'PROJECT_ROLE', 'PM', 1, true);
```

#### 状态转换

| 阶段 | Milestone.status | wf_business_object.status |
|------|-----------------|--------------------------|
| 审批前 | 2 (in_progress) | -- |
| 提交审批 | 2 (in_progress) | 2 (pending) |
| 审批通过 | 3 (completed) | 3 (approved) |
| 审批驳回 | 2 (in_progress) | 4 (rejected) |
| 撤回 | 2 (in_progress) | 5 (withdrawn) |

**审批通过回调**：需在 `GENERIC_APPROVAL` 的 service task 中或通过 `ApprovalEventListener.PROCESS_COMPLETED` 回调更新 `Milestone.status = 3`，设置 `actualDate = LocalDate.now()`。

**审批驳回/撤回**：里程碑回到 in_progress 状态，责任人可重新触发完成。

#### 数据库变更

无新增列。`prj_milestone` 已有 `flowInstanceId` 和 `taskId` 列。

需要新增 `wf_approval_config` 种子数据（见上）。

#### API 变更

**新增**：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/projects/milestones/{id}/complete | 完成里程碑（触发审批或直接完成） |

该端点在 `ProjectController` 或新 `MilestoneController` 中实现。内部调用 `MilestoneService.completeMilestone()`。

#### 实现工时估算

**4 小时**

- 2h: `MilestoneService.completeMilestone()` + 条件判断逻辑
- 1h: 种子数据 + wf_approval_config 配置
- 1h: 回调处理（在 ApprovalEventListener 中增加 MILESTONE 类型的完成回调）

### 场景 2: 任务完成审批

#### 业务规则

并非所有任务完成都需要审批。以下条件满足时，任务完成需要经过审批：

1. **里程碑关联的任务**：`Task.milestoneId IS NOT NULL` -- 里程碑是项目管控点，其子任务的完成需要确认。
2. **关键路径任务**：`Task.type = 'MILESTONE'` -- 里程碑类型的任务本身就是管控点。
3. **高风险/问题类任务**：`Task.type IN ('ISSUE', 'RISK')` -- 问题和风险的关闭需要确认。

**不触发条件**：普通任务（`Task.type = 'TASK'`）且无里程碑关联时，直接完成，不走审批。

#### 触发点

**服务方法**：`TaskServiceImpl.completeTask(Long taskId)`

**当前实现**（`syncflow-task` 模块）：直接更新 `Task.status = 4` (completed)，设置 `actualEnd = LocalDate.now()`。未注入 `WorkflowService`。

**改造方式**：

```
// TaskServiceImpl.completeTask(taskId)
1. 校验: task.status in (1, 2, 3)
2. 判断是否需要审批:
   boolean needsApproval = task.getMilestoneId() != null
       || "MILESTONE".equals(task.getType())
       || "ISSUE".equals(task.getType())
       || "RISK".equals(task.getType());
3. 如果 needsApproval:
   a. 设置 task.status = 3 (pending_review)
   b. 调用 workflowService.startProcess("GENERIC_APPROVAL", task.id, "TASK", task.title, task.projectId, task.assigneeId)
   c. 写入 task.flowInstanceId 和 task.taskIdInFlow
4. 如果不需要审批:
   直接走现有逻辑完成任务
```

#### BPMN 流程

**复用 `GENERIC_APPROVAL`** -- 单节点审批。

```
startEvent → submit(任务负责人) → reviewerApproval(审核人) → endApproved / endRejected
```

#### 审批链

| 顺序 | 节点 ID | 节点名称 | 审批人规则 | ruleType | ruleValue |
|------|---------|---------|-----------|----------|-----------|
| 1 | reviewerApproval | 任务审核 | 任务的 reporter（报告人/创建者） | DYNAMIC | `#reporterId` |

**设计考量**：任务的审批人不是固定角色，而是由任务的上下文决定。使用 DYNAMIC 类型，表达式 `#reporterId` 表示由任务的 reporter 来审核。如果 reporter 与 assignee 是同一人（自建自完），则跳过审批直接完成。

**替代方案**：如果 DYNAMIC 表达式引擎尚未实现（当前 resolveByExpression 为 TODO），则使用 PROJECT_ROLE 规则，审批人为项目中的 PM 或 TECH_LEAD。

```sql
INSERT INTO wf_approval_config (object_type, process_key, node_id, node_name, rule_type, rule_value, priority, enabled)
VALUES ('TASK', 'GENERIC_APPROVAL', 'reviewerApproval', '任务审核', 'PROJECT_ROLE', 'PM', 1, true);
```

#### 审批人解析

当前 `resolveByExpression` 为 TODO。实施时有两种路径：

**路径 A（推荐）**：在 `ApprovalEventListener.TASK_CREATED` 事件中，当 objectType 为 TASK 时，通过业务上下文直接设置审批人为 `Task.reporterId`，不走 ApprovalConfig 查找。这需要在 `ApprovalEventListener.onTaskCreated()` 中增加一个 TASK 类型的特殊处理分支。

**路径 B**：实现 `resolveByExpression`，使用 SpEL 从流程变量中取 `#reporterId`。

#### 状态转换

| 阶段 | Task.status | wf_business_object.status |
|------|------------|--------------------------|
| 审批前 | 2 (in_progress) | -- |
| 提交审批 | 3 (pending_review) | 2 (pending) |
| 审批通过 | 4 (completed) | 3 (approved) |
| 审批驳回 | 2 (in_progress) | 4 (rejected) |
| 撤回 | 2 (in_progress) | 5 (withdrawn) |

**审批通过回调**：`GENERIC_APPROVAL` 的 service task 或 `PROCESS_COMPLETED` 事件回调中，更新 `Task.status = 4`，`Task.actualEnd = LocalDate.now()`。

**审批驳回**：任务回到 in_progress，assignee 可以重新处理并再次提交完成。

#### 数据库变更

无新增列。`tsk_task` 已有 `flowInstanceId` 和 `taskIdInFlow` 列。

需要新增 `wf_approval_config` 种子数据。

#### API 变更

**修改**：

现有 `TaskService.completeTask(Long id)` 方法内部逻辑改造，增加审批判断。对外 API 不变，前端调用方式不变。

```
POST /api/tasks/{id}/complete
```

返回时需区分：如果触发了审批，返回 `409 Conflict` 或带 `approvalPending: true` 的响应体，让前端展示"已提交审批"的提示。

#### 实现工时估算

**6 小时**

- 3h: `TaskServiceImpl.completeTask()` 改造 + 条件判断 + WorkflowService 注入
- 1h: 种子数据 + 审批人解析策略
- 2h: 回调处理（GENERIC_APPROVAL service task 增加 TASK 类型的完成逻辑，或在 ApprovalEventListener 中增加处理）

### 场景 3: BOM 变更审批

#### 业务规则

当 BOM 已发布（status=3）或已锁定（status=4）时，对 BOM 的以下操作需要经过变更审批：

1. **添加 BOM 子项**（`addBomItem`）
2. **编辑 BOM 子项**（`updateBomItem`）
3. **删除 BOM 子项**（`deleteBomItem`）
4. **保存新版本**（`saveVersion`）-- 创建新版本并修改内容时

**不触发条件**：BOM 处于编辑中（status=1）时的修改操作无需审批，直接执行。

**与 BOM 发布审批的区别**：
- **BOM 发布审批** (`BOM_APPROVAL`)：BOM 从编辑中到发布的审批，确认 BOM 结构正确。
- **BOM 变更审批** (`CHANGE_APPROVAL`)：已发布 BOM 被修改时的变更审批，评估变更影响。

#### 触发点

**服务方法**：`BomServiceImpl` 中的 `addBomItem()`、`updateBomItem()`、`deleteBomItem()`、`saveVersion()`。

**当前实现**：这些方法内部调用 `ensureBomEditable(bomId)`，如果 BOM 状态 >= 3 直接抛出 `BusinessException`（"已发布或已锁定的BOM不能直接修改"）。

**改造方式**：

```
// BomServiceImpl.addBomItem(bomId, dto) / updateBomItem / deleteBomItem 改造
1. 查询 BOM 当前状态
2. 如果 status == 1 (EDITING): 直接执行现有逻辑
3. 如果 status >= 3 (PUBLISHED/LOCKED):
   a. 创建变更请求记录（见新增表 bom_change_request）
   b. 调用 workflowService.startProcess(
          processKey  = "CHANGE_APPROVAL",
          objectId    = changeRequest.id,
          objectType  = "BOM_CHANGE",
          objectName  = "BOM变更: " + bom.name + " - " + changeType,
          projectId   = bom.projectId,
          applicantId = SecurityUtils.getUserId()
      )
   c. 返回"变更已提交审批"的响应
4. 审批通过回调中执行实际的 BOM 修改操作
```

**saveVersion 特殊处理**：`saveVersion` 操作本身就是创建新版本，可以走现有逻辑直接创建新 BOM（status=1, EDITING），无需变更审批。变更审批主要针对"原地修改已发布 BOM"的操作。

#### BPMN 流程

**复用 `CHANGE_APPROVAL`** -- 三节点审批。

```
startEvent → submit(申请人) → impactReview(影响评估) → techReview(技术审核) → pmApproval(项目经理) → approveChange / reject
```

变更审批比首次发布审批多了"影响评估"环节，因为已发布 BOM 的变更可能影响下游工艺路线、采购订单等。

#### 审批链

| 顺序 | 节点 ID | 节点名称 | 审批人规则 | ruleType | ruleValue |
|------|---------|---------|-----------|----------|-----------|
| 1 | impactReview | 影响评估 | 工艺工程师（受变更影响的下游角色） | PROJECT_ROLE | PROCESS_ENGINEER |
| 2 | techReview | 技术审核 | 技术负责人 | PROJECT_ROLE | TECH_LEAD |
| 3 | pmApproval | 项目经理批准 | 项目经理 | PROJECT_ROLE | PM |

#### 审批人解析

```sql
INSERT INTO wf_approval_config (object_type, process_key, node_id, node_name, rule_type, rule_value, priority, enabled)
VALUES
('BOM_CHANGE', 'CHANGE_APPROVAL', 'impactReview', '影响评估', 'PROJECT_ROLE', 'PROCESS_ENGINEER', 1, true),
('BOM_CHANGE', 'CHANGE_APPROVAL', 'techReview', '技术审核', 'PROJECT_ROLE', 'TECH_LEAD', 2, true),
('BOM_CHANGE', 'CHANGE_APPROVAL', 'pmApproval', '项目经理批准', 'PROJECT_ROLE', 'PM', 3, true);
```

#### 状态转换

| 阶段 | Bom.status | wf_business_object.status |
|------|-----------|--------------------------|
| 变更前 | 3 (published) 或 4 (locked) | -- |
| 提交变更审批 | 3/4 (不变，保持发布状态) | 2 (pending) |
| 审批通过 | 执行变更，BOM 更新后回到 3 (published) | 3 (approved) |
| 审批驳回 | 3/4 (不变) | 4 (rejected) |
| 撤回 | 3/4 (不变) | 5 (withdrawn) |

**设计考量**：BOM 变更审批期间，BOM 保持发布状态不变（用户仍可查看当前版本）。变更的实际执行延迟到审批通过后的 service task 回调中。

#### 数据库变更

**新增表 `bom_change_request`**：

```sql
CREATE TABLE bom_change_request (
    id              BIGSERIAL PRIMARY KEY,
    bom_id          BIGINT NOT NULL REFERENCES bom_bom(id),
    change_type     VARCHAR(20) NOT NULL,    -- ADD_ITEM, UPDATE_ITEM, DELETE_ITEM, SAVE_VERSION
    change_data     JSONB NOT NULL,          -- 变更内容快照 (变更前/变更后的数据)
    change_summary  TEXT,                     -- 变更说明
    status          SMALLINT DEFAULT 1,       -- 1=pending, 2=applied, 3=rejected
    flow_instance_id VARCHAR(64),             -- Flowable 实例 ID
    requested_by    BIGINT NOT NULL,          -- 申请人
    requested_at    TIMESTAMP DEFAULT NOW(),
    resolved_at     TIMESTAMP,
    resolved_by     BIGINT,
    tenant_id       BIGINT DEFAULT 1,
    created_at      TIMESTAMP DEFAULT NOW(),
    updated_at      TIMESTAMP DEFAULT NOW()
);
```

**新增列到 `bom_bom`**（可选）：

```sql
ALTER TABLE bom_bom ADD COLUMN pending_changes INT DEFAULT 0;  -- 正在审批中的变更数量
```

#### API 变更

**新增**：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/bom/{id}/change-request | 提交 BOM 变更请求（针对已发布 BOM） |
| GET | /api/bom/{id}/change-requests | 获取 BOM 的变更请求列表 |
| GET | /api/bom/change-requests/{requestId} | 变更请求详情 |

**修改**：现有 `addBomItem`、`updateBomItem`、`deleteBomItem` 端点在 BOM 已发布时返回 `409 Conflict`，并引导前端使用变更请求接口。

### 场景 4: 审批委托与抄送

#### 业务规则

**委托 (Delegation)**：
1. 用户可将自己作为审批人的权限委托给他人，支持设置生效时间段。
2. 委托仅在任务被分配到原审批人时生效 -- 任务分配给 A，如果 A 有活跃委托给 B，则任务自动转给 B。
3. 委托可随时撤销，撤销后新的审批任务不再转派。
4. 已转派的任务不受撤销影响（已分配给 B 的任务不会自动回到 A）。

**抄送 (CcRecord)**：
1. 发起审批时可选择抄送人，抄送人能收到通知并查看审批详情，但无需审批操作。
2. 审批每进入一个新节点，自动向抄送人列表发送通知。
3. 抄送人可以标记"已读"。

#### 触发点

**委托 -- 任务分配时**：

委托的触发点不在业务模块，而在 `ApprovalEventListener.onTaskCreated()` 中。当前代码已经处理了 `TASK_CREATED` 事件并动态设置审批人。委托检查应插入到这个流程中：

```
// ApprovalEventListener.onTaskCreated(task, bo) 改造 (插入到现有审批人解析之后)
现有逻辑: resolveAssignees → setAssignee(taskId, userId)
委托检查:
  Long originalAssignee = userId;
  Long effectiveAssignee = delegationService.resolveDelegatedApprover(originalAssignee);
  if (!effectiveAssignee.equals(originalAssignee)) {
      taskService.setAssignee(taskId, effectiveAssignee.toString());
      log.info("Task {} delegated from {} to {}", taskId, originalAssignee, effectiveAssignee);
      // 发送通知给委托人和被委托人
  }
```

**抄送 -- 审批发起时和节点切换时**：

1. 发起审批时：`WorkflowController.startProcess()` 接收可选的 `ccUserIds` 参数，在 `startProcess()` 完成后为每个抄送人创建 `CcRecord`。
2. 节点切换时：`ApprovalEventListener.onTaskCreated()` 中，在向审批人发通知的同时，查询 `wf_cc_record` 中该 businessObjectId 的所有抄送人并发送通知。

#### BPMN 流程

不涉及新的 BPMN 流程。委托和抄送是现有审批框架的横切关注点，附加在所有审批场景上。

#### 审批链

不适用 -- 委托和抄送是审批链的附加行为，不改变审批链本身。

#### 审批人解析

委托在审批人解析完成后执行，是一个"后处理"步骤：

```
原始解析流程:
  ApprovalAssigneeResolver.resolveAssignees() → [userId1, userId2]
  ↓
委托后处理:
  delegationService.resolveDelegatedApprover(userId1) → userId1 或 delegatedUserId
  delegationService.resolveDelegatedApprover(userId2) → userId2 或 delegatedUserId
  ↓
设置到 Flowable 任务
```

**全局委托 vs 单次委托**：

当前 `wf_delegation` 表绑定到 `businessObjectId`，这是单次委托（针对某一个审批实例）。需要扩展支持"全局委托"（针对用户的所有审批任务）：

**方案**：`businessObjectId` 允许为 NULL，表示全局委托。`resolveDelegatedApprover(Long userId)` 查询时先查全局委托（`business_object_id IS NULL`），再查单次委托。

#### 状态转换

委托和抄送不改变业务实体或审批任务的状态。它们是附加行为。

| 操作 | Delegation.isActive | CcRecord.isRead |
|------|--------------------|-----------------|----|
| 创建委托 | true | -- |
| 撤销委托 | false | -- |
| 抄送人收到通知 | -- | false |
| 抄送人标记已读 | -- | true |

### 场景 6: 文件版本发布审批

#### 业务规则

### 4. 可提取的通用模式

#### 模式 1: 变更审批拦截器 (ChangeApprovalInterceptor)

BOM 变更（场景 3）、工艺路线变更（场景 5）、模块规格变更（场景 7）的逻辑高度相似：

```
已发布实体 + 编辑操作 → 创建变更请求 → 启动 CHANGE_APPROVAL → 回调中执行实际变更
```

**建议抽象为**：

```java
/**
 * 通用变更审批拦截器。
 * 任何已发布实体的修改操作，先检查实体状态，
 * 如果需要审批则创建变更请求并启动 CHANGE_APPROVAL 流程。
 */
@Service
public class ChangeApprovalInterceptor {

    private final WorkflowService workflowService;
    private final ChangeRequestService changeRequestService;

    /**
     * 拦截修改操作。
     * @param entityType  实体类型 (BOM_CHANGE, PROCESS_CHANGE, SPEC_CHANGE)
     * @param entityId    被修改的实体 ID
     * @param entityStatus 当前状态
     * @param publishedStatus 已发布状态码
     * @param changeType  变更类型
     * @param changeData  变更数据快照
     * @param projectId   关联项目 ID (可为 null)
     * @return true 表示已提交审批，false 表示直接执行
     */
    public boolean intercept(String entityType, Long entityId,
                             Integer entityStatus, Integer publishedStatus,
                             String changeType, Object changeData,
                             Long projectId, Long applicantId) {
        if (!entityStatus.equals(publishedStatus)) {
            return false; // 不需要审批
        }
        // 创建变更请求 + 启动审批
        Long changeRequestId = changeRequestService.createRequest(
            entityType, entityId, changeType, changeData, applicantId);
        workflowService.startProcess("CHANGE_APPROVAL", changeRequestId,
            entityType, entityType + " 变更", projectId, applicantId);
        return true;
    }
}
```

#### 模式 3: 审批完成回调注册 (ApprovalCallbackRegistry)

当前每个 BPMN 的 service task 通过 `delegateExpression` 直接引用 Spring Bean（如 `${bomApprovalService}`）。随着场景增多，回调逻辑分散在各个 Service 中。

**建议抽象为统一注册表**：

```java
/**
 * 审批完成回调注册表。
 * 每个 objectType 注册自己的 onApproved / onRejected 回调。
 */
@Service
public class ApprovalCallbackRegistry {

    private final Map<String, ApprovalCallback> callbacks = new HashMap<>();

    @PostConstruct
    public void init() {
        register("BOM", bomCallback);
        register("MILESTONE", milestoneCallback);
        register("TASK", taskCallback);
        register("FILE", fileCallback);
        register("BOM_CHANGE", bomChangeCallback);
        // ...
    }

    public void onApproved(String objectType, Long objectId, Long approverId) {
        callbacks.get(objectType).onApproved(objectId, approverId);
    }

    public void onRejected(String objectType, Long objectId, String reason) {
        callbacks.get(objectType).onRejected(objectId, reason);
    }
}
```

这样 `GENERIC_APPROVAL` 和 `CHANGE_APPROVAL` 的 service task 可以统一调用 `ApprovalCallbackRegistry`，而不需要为每种 objectType 编写独立的 service task。

#### 模式 4: BPMN 统一化

当前 7 个 BPMN 文件中，大部分结构相似（submit → review → approve/reject）。`GENERIC_APPROVAL` 和 `CHANGE_APPROVAL` 可以覆盖绝大部分场景：

| 场景 | 当前 BPMN | 建议改为 |
|------|----------|---------|
| 里程碑审批 | GENERIC_APPROVAL | 不变 |
| 任务完成审批 | GENERIC_APPROVAL | 不变 |
| BOM 变更审批 | CHANGE_APPROVAL | 不变 |
| 工艺路线变更 | CHANGE_APPROVAL | 不变 |
| 文件版本发布 | FILE_APPROVAL | 可改为 GENERIC_APPROVAL |
| 模块规格变更 | CHANGE_APPROVAL | 不变 |
| 项目创建审批 | GENERIC_APPROVAL | 不变 |
| 问题/风险审批 | GENERIC_APPROVAL | 不变 |

最终只需要 **4 个 BPMN** 即可覆盖所有场景：

1. `GENERIC_APPROVAL` -- 单节点审批（里程碑、任务、项目创建、问题/风险、文件发布）
2. `CHANGE_APPROVAL` -- 三节点变更审批（BOM/工艺/规格变更）
3. `BOM_APPROVAL` -- BOM 首次发布（含条件路由）
4. `STAGE_GATE_APPROVAL` -- 阶段门审批（含并行网关）

### 5. 风险与注意事项

1. **DYNAMIC 表达式引擎未实现**：`ApprovalAssigneeResolver.resolveByExpression()` 当前返回空列表。场景 2 的任务审批人解析如果使用 DYNAMIC 类型，需要先实现该功能。**建议**：短期使用 PROJECT_ROLE 替代，长期实现 SpEL 引擎。

2. **跨模块依赖**：审批回调（如更新 Milestone.status、Task.status）需要 workflow 模块反向依赖 project/task 模块。**建议**：使用 `ApprovalCallbackRegistry` 模式通过接口解耦，或使用 Spring Event 机制。

3. **并发问题**：多人同时对同一已发布 BOM 提交变更请求时，可能存在冲突。**建议**：使用乐观锁或 `SELECT FOR UPDATE` 确保同一实体只有一个进行中的变更请求。

4. **wf_change_request 的 projectId 为 null 的情况**：模块规格（ModuleSpec）不绑定项目，审批人解析时 PROJECT_ROLE 不可用。需确保审批配置使用 DEPARTMENT 或 USER 类型。

5. **事务边界**：审批启动和业务状态更新应在同一事务中。如果 `startProcess()` 成功但业务状态更新失败，会导致流程已启动但实体未标记。需确保 `@Transactional` 正确传播。
